## Local validation boundary

**Latest fully enabled validation (Phases 0–3 and P4.1–P4.3):** **424 tests** passed, with zero skips, failures, or errors, in two consecutive runs. An earlier run in the same session reported 28 transient Docker-case errors that did not reproduce; the cause was not captured. Each run required the real Docker suite, both optional extras (`SAFETY_LAB_DOCKER_TESTS`, `SAFETY_LAB_TRACEFRAME_TESTS`, `SAFETY_LAB_INSPECT_TESTS` all set to 1), and Docker Desktop engine 29.8.2. All 28 container cases passed on the current tree; no `safety-lab-*` containers remained. Rebuilding from the pinned inputs reproduced the same image ID. [Saved validation evidence](validation/docker-validation.json) records the JUnit hash, 74 source/configuration hashes, the worker identity, and commit `ce62094` plus uncommitted P4.1–P4.3 work. Ruff, strict mypy across 47 source files, the lockfile check, the 10 trusted SQL regressions, and source/wheel builds also passed.

**Phase 2 enabled-Docker validation:** **311 tests** (**283 offline checks and 28 real Docker cases**), with zero skips, failures, or errors. Ruff lint and formatting across 54 files, strict mypy across 27 source files including the worker, lockfile checks, and source/wheel builds passed. A previously verified clean runtime-only wheel install in an external environment validates public fixtures and SQL policy without DuckDB or the private evaluator installed; its pinned dependencies passed `uv pip check`. The private development evaluator passed all **10 trusted SQL regressions** with zero model calls or file writes. [Saved validation evidence](validation/docker-validation.json) records the JUnit report hash, 44 source/configuration hashes, lockfile hash, and worker identity for the enabled run.

Docker cases remain opt-in for ordinary offline development. The earlier unavailable-engine blocker is resolved. The first real run exposed a startup incompatibility: DuckDB 1.5.6 rejects the session-only `enable_progress_bar` option in global connection configuration. Moving it to `SET` before configuration locking resolved all six initially failing cases. After rebuilding, the full expanded suite passed, including genuine typed-decimal USD 200.00 results and independently scored incorrect USD 340.00 results.

The real container suite verified read-only root/input mounts; absence of host/private paths and the Docker socket; a non-root identity, disabled capabilities, no privilege escalation, seccomp, and no external network. Fixed developer-authored container diagnostics observed throttling at one CPU while a concurrent useful SQL query succeeded, a 256 MiB memory ceiling with `OOMKilled` and exit 137, a 64 MiB temporary filesystem returning `ENOSPC`, and a 64-process ceiling returning `EAGAIN`. Both stdout and stderr overflow, wall timeout, and cancellation removed the running containers without returning truncated results. Useful queries still passed after resource stress. Final Docker inspection found no `safety-lab-*` containers left behind. The diagnostics use production resource arguments; they do not extend the analyst's SQL-only interface.

The runtime wheel excludes `evaluator/`, `sandbox/`, benchmark task cards, and private labels; building an image and running private regressions require the source checkout. Excluding files from a wheel is packaging, not actor/evaluator isolation. The diagnostic prints the actual state root for its process; use the absolute `SAFETY_LAB_STATE_DIR` override when switching launch contexts or installations that virtualize Local AppData.

The Docker client and server are now 29.8.2 in the `desktop-linux` context (the Phase 2 run used 28.0.4). `doctor --require-docker`, `safety-lab worker build`, and `safety-lab worker smoke` pass against the local Linux engine. Windows local state and the read-only public input mount work with that engine. With the pinned image present, `doctor` reports `docker_ready` and `sql_worker_ready` as true while explicitly reporting `isolation_validation` as `not_assessed_by_doctor`; boundary evidence comes from the separate suite. The validated image ID is `sha256:7afcc4b3a908da64495217dc43c5d76e39c2c5aa9bd6950bd0e9d6809d96fb7b`; its worker SHA-256 is `15c76bc328f1e642ca1654669f9c927c1631940db93da02680d9ee8a42daec77` and policy SHA-256 is `84da12f0aaaeacc23c80249638b27b6699b7371637743cb1f0e84a5a0956f76c`.
