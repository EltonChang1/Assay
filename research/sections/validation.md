## Validation and deterministic development results

### Evidence scope and reproducible source identity

This report distinguishes three kinds of evidence: executable development regressions, container-boundary integration checks, and a proposed comparative model experiment. The first two have been executed; the third has not. The present evidence supports claims about the implemented vertical slice and its tested behavior. It supplies no estimate of whether an evidence-preserving reviewer reduces errors made by a deployed model. Test cases are selected checks of implementation requirements, rather than a random sample of model behavior or security attacks. Their pass fraction is therefore not a safety rate.

Fresh validation was performed on October 18, 2026, in the client time zone, from parent commit `64a240a82bfcb46ce9ee96af9d0152ea46591365` with the changes described below. The environment used Python 3.12.6 on Windows 11 AMD64, uv 0.6.5, and Docker Desktop's Linux/amd64 engine, with client and server version 29.8.2. Exact installed versions included DuckDB 1.5.6, SQLGlot 30.23.0, Pydantic 2.14.1, pytest 8.4.2, Inspect 0.3.281, and TraceFrame 0.1.0 at the repository's pinned upstream revision. The evidence manifest, `research/validation/current-validation.json`, records source/configuration SHA-256 digests, environment details, commands, artifact hashes, and test accounting. A commit identifier alone would be insufficient because validation included uncommitted source changes; the digest inventory identifies the implementation actually checked.

The initial offline run, after correcting an import-order issue introduced by the package rename, produced 408 passes and 29 skips in 54.15 seconds. Twenty-eight skips were the deliberately disabled Docker suite; the remaining skip checks POSIX file modes that do not apply to Windows. Both optional integrations were installed and required through their test environment flags, so an absent dependency could not silently remove their tests. The offline run predates the additional semantic-regression cases described below. The final post-repair, Docker-enabled run produced **441 passes, one skip, zero failures or errors, and four dependency warnings in 111.25 seconds**. All 28 real Docker cases passed; the sole skip was the Windows-inapplicable POSIX file-mode check. Its separately retained JUnit file is the authoritative count for this report. Ruff linting, Ruff formatting, strict mypy over 48 configured source files, and source-distribution/wheel builds also passed after the repair. The four warnings in each run concerned Inspect's deprecated use of a dependency argument; they did not represent failed checks.

A relocation issue in the existing local virtual environment prevented its `pytest.exe` and `mypy.exe` console launchers from resolving an interpreter embedded under the repository's former directory name. Invoking the same installed tools with `uv run --locked ... python -m pytest` and `python -m mypy` succeeded. No dependency was replaced to bypass that problem. This distinction matters for reproduction: a fresh environment should regenerate console launchers, while module invocation avoids an unrelated stale executable path in a moved checkout.

### Numerical regressions and independent reference truth

The trusted milestone executed ten fixed SQL analyses: five strategies on each of two public synthetic fixtures. Reference truth was computed by an independent Python oracle over canonical order events, rather than by the tested SQL statements or their relational result tables. All ten expected regression outcomes passed. Seven statements returned numerically correct required answers; three deliberately incorrect statements were correctly scored incorrect. Calling this ten successful analyses would obscure the purpose of the negative controls: success means that observed correctness matched the specified expectation.

| SQL strategy | Base result / truth (USD) | Equal-amount result / truth (USD) | Independent score |
|---|---:|---:|---|
| Order aggregation | 200.00 / 200 | 300.00 / 300 | Correct in both |
| Join orders directly to items | 340.00 / 200 | 440.00 / 300 | Incorrect in both |
| Filter orders using EXISTS | 200.00 / 200 | 300.00 / 300 | Correct in both |
| Join to item IDs grouped by order | 200.00 / 200 | 300.00 / 300 | Correct in both |
| SUM(DISTINCT order amount) | 200.00 / 200 | 200.00 / 300 | Correct only in base fixture |

The join failure follows from multiplicity. If eligible order `i` has amount `a_i` and `m_i` matching item rows, the direct join computes the sum of `m_i a_i`; the requested metric sums each `a_i` once. A receipt can faithfully record the wrong expression's execution. The equal-amount fixture supplies the complementary failure: deduplicating values discards a legitimate order whenever two distinct orders share an amount. Correct order identity cannot generally be replaced by unique numerical values. The base fixture alone would not expose that mistake because its distinct-amount answer happens to equal the reference.

The milestone JSON preserves each query result, canonical reference value, slot-level score, and expected-outcome status. It explicitly records zero live model calls and marks both the untrusted-execution boundary and publication boundary as untested by this particular harness. Its host-side DuckDB execution accepts only developer-authored fixed statements. It is a trusted numerical regression tool, not the production route for analyst-supplied SQL. Independent scoring uses the same synthetic generator's canonical records, so the oracle and public tables remain coupled through generation. Distinct implementation paths reduce one form of circular scoring without proving that the task definition or generator is universally correct.

Other deterministic tests cover settled status, currency, half-open temporal boundaries, empty eligible populations, insufficient data, required and permitted supporting slots, historical scope, exact decimal tolerance boundaries, and semantic mismatches even when the reported number happens to match. The base fixture's independent truth is USD 200 across three eligible orders. A historical fixture has a different data basis and USD 190 truth. These are controlled examples, not an empirical distribution of business data.

### A semantic-verification defect discovered during report preparation

Repository inspection exposed a previously untested discrepancy between SQL name resolution and the semantic recognizer. A common table expression named `orders` can shadow the public base relation. For example, a CTE that first restricts orders by amount can be referenced by an outer query whose settled-status, currency, and date predicates look correct. Checking the outer relation's spelling against the literal name `orders` does not establish that it denotes the unmodified public table. Explicit column aliases can similarly change what an apparently familiar field denotes.

Before repair, constructed examples produced genuine DuckDB results of USD 100 or USD 300 against the USD 200 reference while receiving passing mandatory checks. Thus authentic execution evidence and exact claim-to-cell binding were both present; the defect was an unsound interpretation of query structure. The finding is an implementation counterexample discovered through analysis, not a measured failure frequency. It also demonstrates why extensive passing regressions cannot justify a claim that semantic verification is complete.

The repair adds a conservative relation-binding guard. A CTE that shadows either public table name, case-insensitively, or an explicit table-alias column list causes the four query-semantic checks to return `unknown`. Five new regression cases retain passing authenticity and cell-binding checks while requiring unknown semantic outcomes and a `needs_review` decision under the checked publication policy. Previously supported correct alternatives remain accepted. A focused run covering verification, publication, and SQL policy passed 114 cases before the final complete run.

This repair deliberately narrows certification. It does not implement a general SQL equivalence prover or infer arbitrary column lineage. Some excluded queries can be correct. Their unknown status states that the current recognizer has insufficient support, rather than that the query must be false. More generally, unsupported derived-table aggregates, CASE-based expressions, and top-level grouping already produce unknown semantic checks. Conservative rejection or escalation can reduce useful coverage; that cost must be measured in the future study rather than assumed away.

### Container execution and publication checks

The enabled integration suite contains 28 real Docker cases. Four numerical cases execute the base correct total, duplicated join, equal-amount correct total, and distinct-amount failure through the actual gateway and worker. Successful responses preserve typed decimal values, result hashes, worker identity, snapshot identity, durable receipts, and complete bounded results. These cases distinguish the isolated execution boundary from the offline publication harness, which substitutes an in-process DuckDB worker while exercising the real gateway's frozen inputs, result serialization, and receipt path.

The worker build reproduced immutable local image ID `sha256:7afcc4b3a908da64495217dc43c5d76e39c2c5aa9bd6950bd0e9d6809d96fb7b`. Its Python base image and DuckDB/SQLGlot wheel hashes are pinned. An explicit provisioning smoke succeeded before the enabled suite. An image ID identifies locally built image bytes; it is not a claim that an image was published to a registry. The build and smoke records are retained alongside the JUnit artifacts.

Boundary tests exercise worker-side SQL revalidation, an absent approved table, non-root UID 10001, a read-only root and sole public-data bind mount, absent private/host paths and Docker socket, disabled external networking, capability/privilege restrictions, and seccomp behavior. Fixed developer-authored resource diagnostics use production container arguments to test CPU throttling, a 256 MiB memory ceiling and observed OOM kill, a 64 MiB temporary-filesystem ceiling, and a 64-process limit. Timeout, cancellation, and stdout/stderr overflow cases require container removal without reporting a truncated success. Useful work runs concurrently with CPU stress and after resource stress. These are exercised boundaries in a specific local configuration, not an exhaustive security assessment or proof against kernel/container-runtime vulnerabilities.

Publication regressions check exact rendered bytes, revision-bound decisions, source epochs, stale-current-release invalidation, preserved archival history, concurrency, transaction rollback, cancellation races, and process termination during publication. The renderer emits declared typed slots and host-authored surrounding text; arbitrary model prose does not enter released report bytes. An authentic USD 340 claim passes integrity and binding but fails the grain check. A baseline release can still be independently scored incorrect, establishing that the evaluator measures released artifacts rather than equating publication with truth.

### Episode mechanics, historical evidence, and limits of inference

Scripted analyst and reviewer tests demonstrate arms A through E, run-scoped evidence access, strict decisions, one bounded correction round, revision-specific repeated review, and recorded usage. On the scripted duplicated-join example, A and an allowing C reviewer release an incorrect claim, while checked arms B, D, and E withhold on grain. B and E can release a corrected USD 200 second revision. These are deterministic policy-mechanism checks. They do not show that a real reviewer would allow or reject the same content, that E outperforms D, or that equal recorded usage amounts to an enforced common budget. Inspect tests use its offline mock provider. The paid development pilot is a separate run and is reported in `research/paper.md`.

Historical evidence remains separately identifiable. The older committed Docker-validation manifest records 424 passes, zero skips, and 98.59 seconds for an earlier dirty tree, with 74 source/configuration hashes. Before the present repairs, 23 of those hashes matched this checkout and 51 differed; many differences followed the package rename. Repository prose also records a later 436-pass run and hosted Linux validation, but the old manifest was not regenerated for that later count. This report neither substitutes historical totals for fresh results nor independently verifies remote CI from prose. A documented Linux failure caused by owner-only frozen snapshot directories is valuable portability evidence: Docker Desktop's Windows file sharing had masked permissions enforced by Linux bind mounts. That failure was repaired before the present work.

The available evidence does not establish the primary research hypothesis. Final-test information isolation, combined oversight and spending reservations, lease expiry, gateway admission fencing, benchmark diversification, attack development, calibration, preregistration, and confirmatory analysis remain unfinished. No confidence interval, risk reduction, model ranking, or cost-effectiveness estimate can be inferred from test counts. Proposed episode counts and bootstrap procedures belong to the experimental protocol, not the results. The defensible outcome is a tested, limited research system with explicit counterexamples, a newly repaired semantic gap, and reproducible development artifacts ready to support further experiments.
